## 已验证根因与边界

1. 失败请求 `91e695cf-3233-4a36-af91-5885ee38650d` 在 PostgreSQL 中进入 `RUNNING`，对应 pg-boss 任务 `4691cdca-9abf-45d3-8ef6-4cb09708bd3f` 已进行 0—4 次重试。
2. 每次尝试均在 `PostgresExportService.buildInput` 的生成前完整性校验失败，稳定内部码为 `EXPORT_COMPLETENESS_FAILED`；尚未创建 streaming workbook、归档对象或进入下载响应。
3. 当前快照包含 14 个 `INCLUDED`、3 个 `INCLUDED_WITH_WARNING` 和 1 个 `HARD_EXCLUDED` 切片；该硬排除切片有 0 条计算事实。相同处分布的 v6 任务曾成功，v7 校验把“保留排除审计事实”误判为“发布快照整体不可导出”。
4. Worker 将确定性的发布快照校验错误当作瞬时故障交给 pg-boss 指数退避，只有重试耗尽才写业务失败；业务表因此在等待期间长期保持 `RUNNING`。
5. API 的 create/current/list 三条投影路径都把 `RUNNING` 硬编码为 `50`，没有阶段、已处理行数、总行数或业务心跳字段。
6. 全新隔离 schema 首次登录时，管理员引导初始化对 `account_role` 的可延迟唯一约束使用了无冲突目标的 `ON CONFLICT DO NOTHING`，PostgreSQL 以 SQLSTATE `55000` 拒绝；现已改为先锁定查询再插入或更新，并增加全新库回归。
7. 首轮真实导出到达修复后的范围查询时，新增 SQL 把保留字 `month` 用作未加引号的别名，PostgreSQL 以 SQLSTATE `42601` 失败；现已显式引用别名、以迁移集成测试 `PREPARE` 同一查询，并把 SQLSTATE 42 类确定为不可重试的 `EXPORT_QUERY_INVALID`。
8. XLSX 是 OOXML ZIP 容器，旧分类仅凭 ZIP magic 展开中央目录，使开模师 48 个物理文件膨胀为 59 个导入事实，多出 11 个内部 XML/关系条目。现按 OOXML 内容标记将其作为单个不参与计算文件，通用 ZIP 仍执行原安全链；修复后导入事实精确回到 48 个，金额、行数和切片守恒。
9. pg-boss 对 `upload.finalize` 和 `import.analyze` 使用 `batchSize=1`，约 2 秒轮询一次；34 个实际总处理仅约 3.18 秒的分析任务把预检到 COPY 拉长到 69.28 秒。改为每批最多 8 个、批内串行、逐任务结果隔离后，同阶段降至 13.37 秒，下降 80.7%。
10. 批处理后首次 E2E 仅下降 4.73%，但不是队列收益反证：复用同一 schema 时每轮新增约 580,699 条计算结果、数据库关系约增加 486 MB、WAL 约 779 MiB，后轮计算结果插入由 11.51 秒漂移到 21.22 秒。固定状态基准必须每轮使用全新 schema。
